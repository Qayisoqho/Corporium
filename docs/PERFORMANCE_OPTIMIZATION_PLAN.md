## 规模与速度目标

单项目上限按 **10 万句**规划，文本句与独立例句合计。将“数万词条”暂取 **5 万普通词条**作为验收点，共享语素另行计数。同一组数据同时记录不同读音数、标签数、词格数、共享例句成员数、每条记录的引用数与最大分组大小。五万条互不相干的记录和一个被五万处引用的义项，会触发不同的工作。

建议用下表验收索引已经就绪的日常操作。P95 表示一百次约有九十五次可在目标内完成。界面从点击或提交查询开始，计至正确数据、计数和可用控件出现。保存要等数据库事务成功，并显示已提交的值。毫秒均为墙钟时间。

| 日常操作 | 后端 P95 | 界面 P50 / P95 |
| --- | ---: | ---: |
| 普通文本／独立例句检索、翻页，标签定义或同音表当前页就绪 | 50 ms | 100 / 200 ms |
| 高频单字符、全字段含继承释义、大量共享成员或同音项，取默认页并给出精确计数 | 150 ms | 150 / 300 ms |
| 改一句译文、一条备注、一项标签说明或一个读音归类，提交并恢复编辑入口 | 100 ms | 150 / 250 ms |

保存后再点开同一输入框，另以 **P95 ≤350 ms** 验收焦点和实际值。沿用已有的连续 150 ms 无页面变化探针，整页稳定另记，目标 P95 ≤500 ms。已建好索引、关闭再打开应用后的首个正确页面以 500 ms 为初步目标，逐次列值。首次建索引、音系规则大改、全库替换、显式请求“全部”和完整导出，记录真实完成时间、处理行数、峰值内存、取消与恢复。短时显示进度的响应时间单列。

## 第一批 · 文本语料与独立例句检索

**先改共同的命中计算，再改各自怎样取一页。** 已有索引会把相同字符串合并，精确和前后缀走排序索引，包含匹配可先取三字符片段再核对原串。文本搜索已经只展开当前页正文。高频条件仍会在每个请求里把全部命中位置写进临时表，再分组、排序和分页。独立例句库还会取回全部命中 ID，在 Python 中遍历每一个组、逐组查成员、遍历散句、排序，最后取 20 个展示单位。实现入口见[句子检索](../sentence_search_index.py)、[文本工作区](../corpus_search.py)与[例句分组](../example_groups.py)。

1. **句子身份和词格位置分开取。** 复用现有值和位置索引，先对比两条 SQL 路径。一条从罕见值向句子查，一条按当前文本、语言和顺序筛候选，再检查命中。对高频词形试建按“字段、值、句子”去重的窄表，句子身份保留来源类型和稳定 ID。在同一数据库快照先取当前页身份，再取其高亮位置和正文。准确的总句数、去重词格数和语码汇总各用合适的窄索引计算。一个词格命中多个字段时只算一次，文本备注可命中整句但不增加词格数。
2. **翻页复用已经算过的匹配。** 普通前后翻页以稳定排序键续取，随机跳页和末页继续可用。仅在重复计算仍明显时，对昂贵条件短时复用有大小上限的命中身份或分页锚点，键包含项目、数据版本、实际及所属语言、范围、字段、过滤和排序。每个请求新开连接，SQLite 临时表只属于创建它的连接，跨页复用须有明确生命周期。另一窗口写入时按新版本重查，只允许最新请求更新当前页。
3. **独立例句直接按展示单位分页。** 让例句库在 SQLite 内连接同一批命中身份与现有组成员索引，用成员存在性筛组，用无有效组成员关系筛散句。组以有效成员最早编号排序，空组及并列项沿用现有规则。先取 20 个组或散句，再批量取本页成员、语码、标注和媒体摘要。分别算展示单位数、组数、散句数和去重的命中句数。保留同一句跨组、组名／语境独自命中时显示上下文、升降序、语法可接受度和语码筛选的原语义。大组展开、复制和编辑要能取得全部有效成员。
4. **按证据改子串候选。** 长查询目前只取开头三个字符，可比较几个片段的稀有程度，试用更稀有的片段或交集，最后仍作字面核对。短于三个字符时现有路径扫描去重值。只有分段显示“找值”本身慢，才试针对短串的额外索引，并核算磁盘和保存放大。高频词即使只有一个候选值，也可能对应数万个位置。保留 NFC、大小写折叠、IPA 组合符、上下标、字面符号及无 FTS 的旧库路径。[现有搜索语义](SENTENCE_SEARCH_INDEX.md) · [SQLite FTS5 三字符索引的边界](https://sqlite.org/fts5.html#the_trigram_tokenizer)

首个可验收改动选 `ger`、短语素 `n`、翻译“旧术语”和零命中 IPA。对比当前算法和候选算法的第一页、深页、末页、精确计数、词格位置与语码汇总。同步跑实际独立例句入口的空条件、命中与组筛选。若主要成本转到当前页正文、媒体请求或渲染，再依据分段批量读取或复用句卡。

## 第二批 · 语法标签库的进入、保存与检查

打开工作区和保存定义都会调用 `loadGrammar`，它等待 `grammar-audit` 后才绘制定义和检查结果。后台已有独立定义读取、完成结果缓存及可复用的原始检查事实。即使事实可以复用，登记新标签后仍可能遍历全部事件重做分类。保存还会重建语言兼容缩写表。实现入口见[工作区](../web/grammar.js)、[定义与检查](../grammar.py)、[检查缓存](../grammar_audit_cache.py)与[标签改名](../grammar_rename.py)。

1. **标签库先取得可编辑的定义页。** 复用 `grammar-tags`，将定义筛选、排序、分页下放到数据库。定义上显示的用量按同版本的汇总取数。进入检查区时读取问题计数和当前页，切换前后台及保存后合并重复请求。索引首次准备期间标明检查状态，保留人工“重新检查”。
2. **为“这个写法出现在哪里”建立可更新的记录。** 按语言保存原写法、源句身份、词格／成分位置、是否显式标注及相关依赖，建立“写法 → 出现位置”和反向索引。包含目前按普通词跳过、以后可能登记成别名的写法。源句、有效继承 gloss 或附加标注变化时，只更新受影响的位置。汇总表保存已识别用量、未登记候选和问题数，点一项再取该项的实际句子。原拼写用于区分 `ALL/all` 等可能也是普通词的情况。参考规则版本变化时可重建。
3. **区分三种保存。** 改说明或备注只更新定义、受影响的兼容显示和当前行，已有识别结论可复用。新增、删除、改别名或忽略候选，只按旧／新写法找出受影响的位置，涵盖此前未登记的候选。正式符号改名会实际改写研究标注，以反向索引圈出候选后在事务中逐条核实，保留预览、冲突、撤销及原规则。大量改写单独报告每千处耗时。分类或兼容缩写表的写入也分段测量。

分别测首次进入标签库、再次进入、打开问题页、改说明、登记候选后验证原句、改别名和高引用改名。用现成 1,005 条定义材料检验列表，用万句密集库检验分类，用五万句库检验重启后可复用性。留下未缓存的完整检查作为正确性对照。

## 第三批 · 同音语素表的进入、生成与保存

当前生成表格会读本语言的共享语素与词条／语素分析正文，重组每个组分的读音、书写和来源，合并后才分页。声韵调视图还会给全部读音归类再按韵母分页。确认单一读音会把归类写回语言元数据，前端接着重读语言并请求整表。按现有保存分支，只涉及音系元数据的语言变更还会走到全局词典校验，其耗时要在实际保存中取证。实现入口见[同音分组](../homophones.py)、[音系匹配与归类](../phonology.py)、[保存校验](../lexicon.py)与[界面保存处理](../web/homophone-phonology.js)。

1. **按读音直接找稳定语素、组分及来源。** 建可重建的出现记录，区分独立语素、已关联组分和未整理组分，保留构词分析、组分身份、局部读音／书写覆盖、暂代读音及待核对原因。在 SQLite 中先取本页读音或韵母，按需取当前格子所见语素和来源词。一个语素有多个来源时，以稳定身份去重，来源顺序可重现。普通页、声韵调页和侧栏只请求各自实际使用的内容，同屏复用同一分组详情。核对现有界面、导出和“全部”模式读取完整内容的能力。
2. **让分类随材料变化而更新。** 每种语言的同一版声母、韵母、声调匹配规则只编译一次，同一规范读音只自动匹配一次。先复用韵母别名映射，再按耗时决定是否为声母前缀、声调后缀建立树形索引。人工确认独立保存，沿用匹配签名、空声母、歧义候选顺序及 20 项上限。修改一个读音时，更新其新旧分组、待核对计数及受影响的来源。修改共享语素要追到引用它的活组分，同形编号受影响时同步更新同形项。整套规则变化可使许多自动归类过期，应显示真实重算进度。
3. **拆开三条保存路径。** 分别量单个读音人工归类、编辑语素／组分读音、修改音系清单或批量确认。计时含写入、冲突核对、词典关联校验、撤销记录、提交、重读语言和整表刷新。单项人工归类可凭实际前后记录验证只改本语言的一项，复核分类合法性，提交后只更新旧格、新格、待归类列表和分页。选中若干读音批量确认时先查选中读音。若证实整份元数据重写是瓶颈，再把人工确认迁入有版本的逐读音记录，并验证旧项目、备份、导入和撤销能无损还原。人工决定始终作为研究数据保存。

验收分别从打开面板、生成首个正确表格、返回已生成面板、翻页、点来源词和确认后继续编辑开始计时。现有五万句库缺少音系清单和人工归类。复用已有十二韵母分页材料及重匹配、真实来源关系用例，覆盖多音、同形、暂代与配置更改后待复核。另在同一份工作库核对超大读音组。

## 怎么实施与判定通过

1. **同一批材料贯穿各阶段。** 从现有材料目录选择小型多语／分组项目、万句密集关联库和已有五万文本句＋五千独立句的两个用途不同的快照。大库另有五千词条、五千共享语素和约 131 万词／语素单位。复用已有共享例句、1,005 标签、十二韵母与撤销用例。正式测速前登记每份库的命中分布、组成员与引用分布、索引就绪情况及配置。上限验收若仍有数量或分布缺口，只在**一份可重复使用的隔离工作库**补差额，复用它测试所有模块和界面语言，记录补充项。
2. **先拿到三个工作区的端到端基线，再按前三批逐一交付。** 搜索覆盖无／单／稀疏／高命中，一至二字符、长串及四种匹配模式，单文本／全项目、文本／独立／混合来源。每种路径选能触发差异的代表案例。例句库另测一条句子属于多组、组名独中、散句和深页。语法、同音各测初入、重复进入、单项保存、受影响成员很多的修改及撤销。数据库预热后的应用重开、索引首次建立、一个来源变脏后的首查分别列出。
3. **每条路径有完整的时间账。** 普通跑次不带剖析。用同一动作另跑探针，分开记录桌面请求排队／任务轮询、SQLite 匹配和临时排序、页外正文解码数、同步校验／撤销／提交、响应字节、浏览器脚本／布局绘制及实际再编辑。SQL 同时留查询计划、候选值数、命中身份和位置数，分清查值、扩展、排序及装载成本。保存记录受影响行、索引增量、写入量。关联同一次点击的请求，避免把重叠时间相加。[界面计时方法](FRONTEND_RESPONSE_TESTING.md) · [SQLite 查询计划说明](https://sqlite.org/eqp.html)
4. **用等价结果和分位数验收。** 先用原读取器／完整审计逐项对照，然后在同机同库、同索引状态交替跑前后版本。日常代表项预热后各取至少 50 次，列 P50、P95、最慢一次、响应字节、峰值内存、索引磁盘与首次建立时间。重开应用至少 5 次，单列文件缓存状态。中英文、常规及窄窗 150% 字号从同一数据库复核真实键盘续编和研究字体。20、100 句页分别报告。发布门槛同时核对准确总数、顺序、位置、已确认归类、共享身份、事务和撤销。版本相同的读取可重用，改动、外部写入、恢复备份、旧库升级、写入失败与取消后须返回正确版本。派生索引有版本、能重建。人工标注、人工音系归类保留在正式备份中。

新增索引要同时核算读、写、重建三项代价。仅既有标量／词形和语素形式两阶段索引，五万句基线就用了 306 MiB，首次准备分别耗时 68 和 72 秒。新结构以实际节省的每次查询时间、每次普通保存多写的行数与字节、额外磁盘和重建时间作取舍。源记录与其待更新标记在同一事务提交，后台按版本分批处理，取消或崩溃后只发布完整版本。索引尚未就绪时使用已验证的读取器或明确等待准备，保证看到当前数据。源记录变化范围明确时按模块失效，避免一次无关备注保存令全部读音和标签统计过期。

第一轮实现以五万句上“高频词形只看 20 句”为对照。先交付逐项结果一致的新旧查询计时和独立例句分组对照。如果仍超出目标，继续处理耗时最大的步骤，达标后再推广到其余字段。每批记录真实达到的规模、分布与耗时，最后再给出十万句上限的验收结论。

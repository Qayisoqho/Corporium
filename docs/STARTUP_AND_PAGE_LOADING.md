## 结论与发布边界

等待来自几类不同的工作：打开项目前的检查、备份和重复初始化；首页的整库抽样与隐藏语料页预加载；大量小请求在桌面项目锁下排队；编辑器仍搬运全库词典正文；标签及分析入口同步维护派生数据；最后还有样式重算、布局和字体就绪。应逐项缩小实际工作量，不能把全部等待归为 JSON 解析。

本机已安装程序的首页等静态资源仍对应此前同号发行。检查冻结模块目录，没有上一轮源码新增的 `analysis_counts`、`statistics_facts`、`sentence_scope_index` 和 `dictionary_relations`。因此近期源码改进尚未进入正在使用的安装版；这也不能解释全部启动等待，因为当前源码同样存在下面的路径。本轮不重建安装包。

即使不加载任何项目，安装版的两个后续启动样本也要约 2.43 秒到原生 `loaded` 事件。当前源码不加载项目，到页面就绪条件的三次中位数约 2.37 秒。原生窗口、WebView2、静态资源及脚本启动本身有成本；普通切页达到百毫秒，与整个应用启动达到百毫秒，是两项不同目标。

## 材料、时点与限制

继续复用两份已有隔离材料，没有再生成十万句项目：

- 小项目：已有 Tëlira 隔离示例，573 词条、168 文本句，数据库约 9.1 MB。
- 上限项目：既有 50,000 文本句、50,000 独立例句、50,000 普通词条和 5,000 共享语素，含历史快照及派生缓存，本轮数据库文件约 3.55 GB。文件体积不能外推为所有十万句项目的必需体积。

普通浏览器实验为本机 Edge、Docoid、1440×1000、100% 字号，核对实际 `document.lang` 为中文／英文。每份材料、每种语言测七工作区首次进入及三次重复，再测同音表、音系、笔记、管理和许可；共 136 次。另测词条详情与编辑窗口共 16 次，合计 152 次普通操作，无脚本错误或失败响应。这里测量导航及打开，未保存研究内容，也未把本轮当成窄窗排版验收。

计时严格分开：

1. **导航主流程完成**：真实点击开始，等待既有 `setWorkspace` 的异步链完成，包括读数、草稿／位置保护等；不等同于首次像素绘制，也没有宣称所有输入已逐一测试。
2. **面板出现条件**：详情身份已切换，或原生弹窗／面板已打开；后续内容仍可能变化。
3. **稳定时间**：请求及响应体读取结束，字体就绪，长任务／检索／页面过渡退出，并连续 150 ms 没有相关 DOM 变化，再观察一帧。这个 150 ms 是测量所用的观察窗口，不是产品强制等待。
4. **后台处理与排队**：隔离预览保留真实桌面处理器，加记录分别观察处理总时长和取得项目锁的等待；两者包含关系明确，重叠请求不相加。

重复进入仅三次，报告中位数，不作 P95。系统文件缓存未清空。剖析、首次派生重建和原型均单列。原生启动采用实际 `desktop.main()`／已安装 exe 的隐藏自检窗口；隐藏窗口没有可比较的 paint 记录，报告原生事件与应用就绪标志。源码探针预先导入桌面和 WebView 模块以挂接计时，包含导入耗时，但顺序与普通入口略有不同；解释器在探针开始前的 1.7–2.8 秒没有算成产品模块导入，也不能套到冻结程序。

正式 `data` 和 `github/data` 未以 SQLite 打开。对真实最近项目仅读取配置与文件大小，约 131 MiB；未打开该数据库。因此下面的大库时间用来定位和评估规模效应，不是对用户实际项目的直接测速。

### 重复分类登记是初始化的首要问题

`desktop.py` 的 `Projects.open` 在创建主窗口之前完成完整检查、完整备份和 `server.init`。其中 `lexicon.initialize` 又调用 `categories.initialize`，每次重新读 50,000 条词条正文并登记用法。

带剖析的另一轮初始化约 31.8 秒：`register_usages` 调用 50,000 次，`ensure` 调用 105,005 次，SQL 执行累计占主导；JSON 解码累计约 1.78 秒。分类表只有 17 行。该路径经过 `executescript` 后没有覆盖这批读取的显式事务；分类已经存在时，查询不会通过写入自然开启事务，大量微小 SELECT 反复承担自动读取事务的开销。

同一连接的 1,000 次既有分类查询，三轮自动事务各约 276–296 ms；包在显式读取事务内各约 4.9–6.0 ms。进一步只在隔离进程为现有分类初始化补齐事务边界，完整 `server.init` **31,635 → 4,583 ms**，分类阶段 **26,975 → 999 ms**。分类的所有行逐项一致，研究内容版本不变。这是确定收益较大的第一项，但仍需在正式接入时保证失败回滚、首次迁移和既有外层事务的正确性。

### 首页等待了全库抽样、完整字体目录和隐藏语料页

`homepage.overview` 为抽出最多 24 句，先遍历两种来源，用 JSON 字段提取句子、语言和译文并去重。本库有 95,000 个候选身份。候选的内存缓存上限为 24 MiB，本库估算条目成本超过限额，写入被跳过；因此重复进入首页也可能重新扫描。重启后内存缓存也不存在。

首页的进入按钮还同时等待 `homeRestored`、`corporiumFontsReady` 和 `document.fonts.ready`。而 `homeRestored` 又间接等待最初的 `corpusReady`：尚未进入文本工作区，已经在读取及布置隐藏的语料首页。完整系统字体候选目录也进入首屏等待链。

普通上限库浏览器首轮，页面 DOM 约 600 ms 已建立，应用就绪标志到 6,655 ms 才出现。一个分段请求中，首页处理约 2,076 ms；后发的标签目录和搜索字段请求，其中约 2,010／2,029 ms 在等项目锁。字体目录客户端约 3.9 秒，其中实际处理约 1.9 秒、锁等待约 0.6 秒，另含浏览器连接排队；不能把这个数字全记为字体枚举。

隔离原型把**当前有效版本**的去重候选身份放入约 4.87 MB 的窄 SQLite 目录，仍使用原抽样函数，再按身份读取同样的 24 句。相同随机种子下完整返回内容一致：单次后台 **1,272 → 19.6 ms**；另十次约 17–42 ms。目录额外写入约 171 ms，首次提取候选的原有 1.27 秒仍须付出。原型只证明稳定版本的读取收益，尚未实现正式的逐句增量维护。

当前／原型 HTTP 预览交替各三次，从浏览器导航到首页就绪的中位数 **5,269 → 2,230 ms**，同为 7,029 个 DOM 节点，字体与页面代码保持。它不包括项目初始化或原生窗口启动，不能称为整个应用启动只需 2.23 秒。字体目录的 30 秒缓存等也使小样本有波动。

### 缓存命中后，样式与导航保护的比例变高

小项目的一次缓存词典切换只发出一个撤销状态请求：客户端约 44 ms，后台处理约 14 ms；脚本约 13 ms，样式重算约 70 ms，布局约 3 ms。另一次缓存文本切换的后台约 19 ms、样式约 104 ms。保留草稿、滚动位置、字体和两帧定位等完整导航链后，主流程仍需一百余毫秒，再加稳定观察窗口。

所以“稳定 250–350 ms”有时意味着主体在约 60–170 ms 已完成，后面还在确认稳定。也有真正的渲染成本：大项目详情切换样式重算约 152–181 ms，多次重算和装饰不能由单条 SQL 加索引解决。后续应缩小失效节点范围、合并读写布局和同一轮装饰，保留草稿保护与滚动还原。

笔记、管理和许可等面板在本轮出现条件约 8–11 ms，稳定约 210–293 ms；音系弹窗出现条件约 43 ms，大库稳定约 460 ms。同音表单纯切入约 10 ms，首次生成在大库中英文分别稳定于约 827／545 ms。这些状态与后台生成、全部内容就绪要分开。

### 小请求仍在全局锁下串行，旧页面任务会影响下一页

桌面处理器用同一项目锁包围大多数完整 GET／POST 处理，部分静态和字体请求也会参与排队。浏览器的 `Promise.all` 并不能让这些读取同时执行。轨道波形路径在锁内调用 `media_engine.wave_data`，首次还涉及音频依赖加载、解码和图块准备。离开轨道后，尚未结束的波形工作仍可能挡住下一个工作区请求。

本轮大库独立例句库首次进入发出 24 个请求，其中 **20 个逐卡片 `/api/object-media`**。主列表处理约 659 ms，每个空媒体读取也有约 16–25 ms 后台成本；这次页面的脚本约 263 ms、样式重算约 342 ms。应按当前页一次取媒体状态及关联装饰，并在同一轮插入；批量请求仍须保持每张句卡的身份。

不能直接删掉项目锁：安全的改法是短锁捕获项目路径／代次，工作线程用独立读取连接及一致快照处理，响应发布前再核对项目代次；切项目、写入与读取失效的规则要明确。后台波形应避免占据前景项目锁，区分离页可取消的预览和用户明确发起的研究任务。

### 词条编辑器仍下载全部正文

另外测了两条既有词条及返回第一条，再打开完整编辑器，中英文共 16 次：小项目详情稳定约 381–516 ms、编辑窗口约 579–704 ms；大项目详情约 **755–1,104 ms**、编辑窗口约 **1,642–1,810 ms**。

详情一次常有 10–14 个请求。`workspace-loading.js` 的预备读取仍调用旧的不分页 `dictionary-examples`，真正渲染又请求 `paged=1` 的新接口；两者键不同，产生重复路径。旧请求在这组样本中自身处理很短，但锁排队很明显，不能把整个客户端时间都归为旧接口计算。

编辑器更直接：没有 `entry_id` 的 `/api/morphology-options` 返回 **55,000 条词条／语素及其 body，40,875,201 字节，约 41 MB**。中英文普通打开时该请求后台约 835–853 ms，直到响应体处理结束约 1,099–1,136 ms，随后还要建立编辑控件。详情读取已经限制直接／反向关系；编辑器仍调用全量选词目录。

只把原生下拉选项限制为 50 个节点，并没有消除这份全库响应。应复用数据库选词分页，编辑器先取分类、标签、书写类型与当前已选引用的小目录；只按需补读候选／已选记录的显示字段和形式，避免为选词搬运每条正文。保留已删除或其他语言引用的提示、现有形式选择、搜索、键盘和草稿身份。

## 两个入口还在前景做派生维护

### 分析列表会同步删除过期的大缓存

`analysis_workspace.listing` 在返回最近结果前执行 `DELETE FROM analysis_runs WHERE version<>?`。删除会连带处理统计词频与位置目录，进入工作区因而可能先做大量写入。

受限预览初轮曾观察约 4.65 秒的该请求，但该轮存在测试预览对 `timeline-prepare` 的错误拦截，整轮未列入上表。随后用正常处理器重跑，并单独在事务保存点中验证：仅一份有 45,014 个词频行的过期结果，原列表读取约 **359 ms**；只过滤可见元数据、推迟物理删除的原型约 **0.245 ms**，完整列表响应一致，试验后全部回滚。

这还补出上一轮验收遗漏：计词运行路径虽然能按统计依赖复用缓存，但列表入口仍按全项目版本删除结果。普通备注或译文使全局版本变化后，先进入分析页可能把本可复用的计词结果及其分页索引删掉。上一轮直接重复运行的测试没有覆盖这个“先经过列表”的顺序，不能据此前结果宣称整条界面入口都已保留缓存。

正式修复应分开“哪些版本能显示／复用”和“何时回收磁盘”：按实际查询／统计依赖判定有效性；最近列表只读窄元数据；过期且无引用的派生结果在空闲时分批清理，显式保存的快照和研究证据保持原有保护。还应串联“保存备注／译文→切入分析→重跑→翻页”验收。

### 标签库的首次准备与重复进入仍有全量扫描

本轮大库中文首次标签库主流程约 **47.1 秒**，在全量准备完成前任务弹窗使操作等待；英文是在同一库准备后进入。重复进入仍约 0.5 秒主流程，约 0.68 秒稳定。

独立带剖析的已准备读取约 591 ms，其中 `grammar_usage.prepare` 约 415 ms；即使没有内容变化，也做缺失、孤儿及分组检查。前端还有重复 registry 探测以及任务启动／轮询／遗忘，常见六个请求。

另一事务试验只清空可重建的标签解析表，保持原始材料，结束后回滚并核对内容版本及行摘要。重新准备 65,025 个配方约 19.54 秒；`LEFT JOIN ... WHERE l.revision IS NOT r.revision LIMIT 300` 执行 **218 次，累计约 11.28 秒**。每取一批又从已准备前缀查起，导致重复扫过越来越多的既有行。其余还有逐词处理成本。这个 19.54 秒是独立剖析的子阶段，不是从 47.1 秒普通界面样本中直接拆出的占比。

应一次确定窄的待更新身份／修订集合，或维护与源记录同事务的脏项队列，按身份批次取正文；避免每批重扫已完成前缀。未变化时用版本／完成证明直接返回；前端合并重复探测，真实需要重建才启动任务。定义列表可以先展示，但用量、未登记项和保存校验必须标明其有效版本，不能用旧用量冒充已完成。

## 建议实施顺序与验收

| 顺序 | 具体工作 | 已有证据与验收重点 |
